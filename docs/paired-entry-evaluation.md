# مقایسهٔ prospective تصمیم ورود — ۲۳ اکتبر ۲۰۲۶

این مسیر آزمون کاغذی است؛ هیچ transport خصوصی والکس ندارد. انتخاب عملیاتی فعلی GPT-6-luna و رقیب واجد شرایط Claude Sonnet 4.6 هستند؛ نتیجهٔ مالی آن‌ها هنوز معلوم نیست. هزینهٔ مدل معیار انتخاب نیست و ledgerهای اصلی، سقف تاریخی BoxAPI و binding کلیدها حفظ می‌شوند.

## قرارداد قبل از مشاهدهٔ نتیجه

`scripts.run_paired_paper` یک coordinator و چهار دفترکل مجازی مستقل دارد: hold با ریسک مشترک، قاعدهٔ fee-aware موجود، BoxAPI و APMix؛ cash ثابت نیز گزارش می‌شود. هر دفترکل پنج میلیون تومان مجازی، سقف debit برابر ۱۵۰هزار، کف notional برابر ۱۰۰هزار و یک موقعیت دارد. این عدد مجوز افزایش سقف واقعی ۱۰۰هزار تومانی نیست.

مدت پیش‌فرض ۹۰ دقیقه و دو پنجرهٔ مساوی از پیش ثبت‌شده است. horizon ثابت ۳۰ دقیقه، تحلیل حداکثر هر پنج دقیقه و پایش حفاظت هر ۶۰ ثانیه است؛ هنگام انتظار مدل، حفاظت هر سه ثانیه نیز بررسی می‌شود. دو مدل همان shortlist، ویژگی‌های علّی و cutoff را دریافت می‌کنند؛ فقط cash هر دفترکل جداست. همهٔ ورودها پس از پایان هر دو مدل و با یک book تازهٔ مشترک برای هر نماد سنجیده می‌شوند. دادهٔ خراب، WAIT، fallback، رد میزبان و خطا حذف نمی‌شوند.

فهرست، پنج نامزد نخست غربالگر quant موجود از بازارهای عمومیِ پس از حذف ممنوع‌هاست؛ این حساب اعتباری مجاز زنده را احراز نمی‌کند. خروج صرفاً توسط host با stop/trailing/horizon/deadline اجرا می‌شود. این آزمایش **اثر تصمیم ورود روی shortlist میزبان** را می‌سنجد، نه انتخاب پژوهشی کل بازار یا Position Reviewer کامل. hold فقط یک بار فرصت ورود دارد و تابع ریسک مشترک است؛ buy-and-hold بدون قید نیست. قاعدهٔ ساده forecast ندارد؛ گیت اقتصادی forecast فقط روی تصمیم دارای forecast اعمال می‌شود، مطابق مسیر موجود میزبان.

کارمزد taker برابر ۰٫۳٪ هر سمت، لغزش ۰٫۰۵٪، قیمت بدترین سطح لازم برای کل quantity، محدودیت limit، تازگی و قواعد min/step همان موتور موجودند. پرشدن paper، اولویت صف یا fill واقعی صرافی را اثبات نمی‌کند. barrier مشترک اثر اختلاف سرعت مدل بر زمان ورود واقعی را حذف می‌کند؛ latency هر مدل همچنان در trace مستقل باقی می‌ماند.

## اجرا و توقف

```powershell
.\.venv\Scripts\python.exe -X utf8 -u -m scripts.run_paired_paper --run --run-id paired-entry-forward-20261023-1 --keys-file data/private/provider-credentials.json --duration-seconds 5400 --public-get-cap 1200
```

بدون `--run` حتی کلید و DB خوانده نمی‌شوند. قبل از HTTP وجود ledger اصلی هر دو provider الزامی است. run ID تکراری و resume خودکار رد می‌شوند؛ ایجاد DB جایگزین یا refund نداریم. protocol و source fingerprint قبل از جمع‌آوری ثبت و source هر چرخه کنترل می‌شود. کد حین اجرا منجمد است. برای توقف، فایل `STOP_REQUESTED` داخل پوشهٔ همان run بسازید؛ coordinator پس از انتظار محدود درخواست جاری، ورود را می‌بندد و خروج هر دفترکل را مستقل تلاش می‌کند. timeout مشاهدهٔ ترمینال پایان worker نیست.

`progress.json`، `round-*.json` و manifestهای هر دفترکل شواهد جاری‌اند. `report.json` فقط در پایان، `COMPLETE/PARTIAL`، residual و خطاهای خروج را جدا ثبت می‌کند. raw مشترک در پایان برای replay هر دفترکل کپی می‌شود؛ manifest جاری قبل از این کپی بستهٔ replay مستقل کامل نیست.

## سنجش و محدودیت

بازده خالص، هزینه، افت، peak exposure، تعداد سفارش/fill/round-trip و replay حسابداری ثبت می‌شوند. PnL هر round-trip از بسته‌شدن واقعی ledger و حذف بهترین معامله محاسبه می‌شود. سناریوی اضافه‌شدن ۲۵٪ به کارمزد quote فقط روی معاملات ثابت اجراشده محاسبه می‌شود؛ تغییر تصمیم/quantity/صف/تأخیر را شبیه‌سازی نمی‌کند و حساسیت کامل استراتژی نیست. خروجی کلی و پنجره‌ها باید پس از پایان با زمان‌ها و equity tape بررسی شوند؛ چند معامله، سود آینده یا اجازهٔ live نمی‌سازد.

اجرای تاریخی سه‌ساعته ۱۳ تصمیم معتبر مدل داشت و همه WAIT بودند؛ هیچ ENTER معتبر برای ردشدن در ریسک ثبت نشد. ۱۰ fallback و ۱۱ رویداد غربالگر/میزبان جدا هستند. صفر معامله، شاهد موفقیت یا آلفا نیست. این آزمایش تازه به‌دنبال شواهد اقتصادی مشترک است و خروجی صفر یا منفی هم حفظ می‌شود.

## اصلاح دوام سفارش خروج

تست integration همین مسیر آشکار کرد که `PaperBroker.finalize_portfolio` fill فروش نهایی را در ledger ثبت می‌کرد، ولی سفارش فروش را در جدول `broker_orders` پایدار نمی‌کرد؛ بازیابی حافظه آن را حذف و replay کامل را ناسازگار می‌کرد. INSERT سفارش اکنون در همان تراکنش fill، intent و حفاظت است. تست خرابی درج، rollback پول/موجودی/سود/intent/fill/stop را بررسی می‌کند؛ تست کامل coordinator نیز manifest تا replay را پوشش می‌دهد. این اصلاح مربوط به paper است و UNKNOWN مالی قبلی را حل نمی‌کند.

اعتبارسنجی این فاز: ۴۴۷ تست هسته در ۵۸٫۱۷۵ ثانیه و ۱۱ تست داشبورد در ۱٫۸۲۲ ثانیه پاس؛ Ruff قفل‌شده، compileall، چهار self-check و config نمونه پاس. تست‌های جدید مصنوعی‌اند؛ نتیجهٔ provider/بازار تازه باید از artifact اجرای واقعی خوانده شود.

## وقفهٔ نخست و اصلاح قرارداد عددی

`paired-entry-forward-20261023-1` روی349e136 با۱۳GET عمومی، یک WAIT معتبر از هر مدل و صفر سفارش/fill پس از۱۰۴ثانیه `STOPPED_FLAT/PARTIAL` شد. خروجی قبلی و مصرف مدل حذف یا reset نشدند. book واقعی Wallex quantity/price عددی دارد که decoder به Decimal تبدیل می‌کند؛ کپی با json.dumps و hash همان شیء TypeError ایجاد می‌کرد. hold در این run به همین خطای میزبان رد شد؛ پس مقایسهٔ اقتصادی معتبر حاصل نشد.

کپی با deepcopy مقدار و نوع Decimal را حفظ می‌کند؛ hash JSON ضبط‌شده Decimal را با رشتهٔ دقیق نمایش می‌دهد. تست مشترک و integration ابتدا دادهٔ رشته‌ای داشتند؛ اکنون Decimal را در هر دو مسیر دارند. regression ابتدا قرمز و سپس پاس شد؛ شش book واقعی ذخیره‌شده نیز آفلاین، با۰HTTP/۰سفارش بررسی شدند. یک failure مستقل تست مرگ worker هم نشان داد launcher محیط مجازی Windows PID جدا از مفسر صاحب lock دارد؛ harness اکنون مفسر پایه و source path صریح را اجرا می‌کند تا kill همان صاحب lock باشد. منطق قفل production ضعیف نشد. ۳۱ تست مرتبط در۴٫۰۲۹ثانیه پاس شدند؛ log نخستین failure محفوظ است. اجرای بعدی الزاماً run ID و revision تازه دارد.

پس از اصلاح Decimal و harness، مجموعهٔ کامل دوباره۴۴۷تست در۵۷٫۱۸۶ثانیه پاس شد؛ Ruff/compileall/diff نیز پاس.
